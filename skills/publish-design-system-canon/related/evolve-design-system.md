# Evolve Design System

Turn an approved system posture into a concrete, reviewable canon proposal without implementing it in code.

## Packet mode

- **Carried:** use and update the supplied valid Design Work Packet. Do not reconstruct its intake or reread pinned authority merely to confirm it.
- **Direct single-skill:** when the scoped system proposal is the complete requested outcome, return it without creating a packet.
- **Direct expansion:** when direct system evolution becomes a material or uncertain multi-skill chain, create exactly one [Design Work Packet](../references/packet-projections.md#design-work-packet) before the first downstream handoff, using the [governed-view assembly](../references/packet-projections.md#governed-view-assembly) from the existing sources and native records.

Refresh a carried packet only when a required field is missing, a source is stale or conflicting, scope or authority changes, or genuinely new evidence appears.

Without a valid packet, read [authority and status](../references/authority-and-status.md). Load [design-system craft](../references/design-system-craft.md) and the [Design-System Change Proposal template](../references/audit-exploration-templates.md). Load [practical design checklists](../references/quality-checklists.md) only for the relevant system lenses.

## Preconditions

Require an evidence-backed assessment, exact scope, current effective canon or its confirmed absence, protected boundaries, and an approved posture. Follow stricter consumer policy. Otherwise, an explicit scoped instruction or selection from the user commissioning the task is valid posture authority.

Do not use this skill for evidence-backed `consume`. Proceed directly under the effective canon. If the posture is still materially undecided, complete safe analysis and candidate drafting. Then return findings, viable options, recommendation, trade-offs, and the bounded human choice.

## Produce the smallest change that works

Author one native proposal containing the exact proposed change, alternatives/recommendation, trade-offs, scope, acceptance and adoption/verification information, unresolved questions and the exact human decision being requested. Its ID/revision and authority remain distinct from the Design Contract. The required brief and packet are assembled from this same proposal and the other native records, not separately composed versions of the design.

Choose only the artifacts required by the posture:

- **extend:** add the missing token relationship, component or pattern contract, states, usage guidance, and acceptance criteria while preserving the healthy base;
- **repair:** tighten or replace the deficient rule, document affected states and exceptions, and define adoption and verification;
- **constrain:** define the safe subset, prohibited or unreliable uses, temporary exceptions, debt, and exit condition;
- **establish:** create the minimum coherent tokens, component or pattern contract, states, documentation, and ownership needed for the approved scope;
- **replace-migrate:** define the target contract, compatibility boundary, migration stages, deprecation, exception handling, verification, and rollback.

The proposal may include concise semantic token/theme relationships, component or pattern requirements, behavior/content/state tables, usage/avoid/known-non-fit documentation, agent-ready retrieval context, evaluation fixtures, adoption/drift controls, exceptions, or a migration plan. Keep the proposal in Markdown and technology-neutral unless approved consumer constraints require otherwise. Do not write implementation code, framework APIs, a database registry, schema engine, or package runtime.

## Validate and seek effectivity

Check authority lineage, internal consistency, accessibility and full-state coverage, affected consumers, migration risk, acceptance criteria, and conflicts with protected boundaries. Apply non-material corrections immediately.

Mark the change `proposed` or `review-ready`. Present the exact scoped change, preserved behavior, risks, trade-offs, adoption or migration impact, evaluation, and verification plan to the human effectivity authority. The agent cannot make the change effective.

Once the human explicitly approves the exact proposal under applicable policy, route it to [publish-design-system-canon](../SKILL.md). That workflow provides durable consumer-owned publication, revision/supersession lineage, retrieval metadata, and adoption receipts.

In carried or direct-expansion mode, mechanically materialize the following packet values from the native proposal, its exact posture authority and actual workflow events:


- the current step;
- the System Change Proposal locator, revision, and status;
- the approved posture source;
- findings to preserve;
- the resolved posture gate;
- the effectivity gate;
- the active sequence;
- the next step and stop.

In direct single-skill mode, return the native proposal without a Design Work Packet.
