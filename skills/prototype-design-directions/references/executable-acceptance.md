# Executable acceptance artifacts

Use this reference when a commissioned interaction check has a compatible execution binding or an executable AC is carried into validation, handoff or parity. Ordinary routine conformance retains its compact handoff. Existing source, authority, freshness and review-ready rules remain in [native delivery](native-design-delivery.md).

## Bind the check and its scope

Resolve the supplied API/capability description, runtime/environment and controlling source revisions. Identify which observations it supports and which source obligations need other concrete checks. Use the native acceptance index for this mapping; a separate contract or inventory form is unnecessary.

A fixture-specific API is not a product-wide interface. An unavailable observation limits its dependent evidence; it supplies neither a new product ambiguity nor a request for new owner policy. Continue independent authorized design work and retain the missing observation status.

## Author the native procedure

Write the procedure as the actual executable artifact using the supplied interface. Its setup, actions and observable assertions must preserve the original source conditions, including applicable combined states, history and recovery. Identify the artifact, its revision and accessible file, the controlling source units and its supported scope. Existing normative text retains its original authority.

Freeze the exact code before any authorized execution. Within the commissioned budget, execute that same complete artifact against the independent reference, supplied source-conforming presentation/implementation variants, and source-backed defective variants. Keep acceptance of permitted variation and rejection of defects as separate measurements. A helper-only calibration does not establish that the delivered procedures use it correctly. Use the supplied binding to observe the relevant visible result; an implementation-specific selector identifies that observation and does not create a product markup or formatting requirement.

Record each exercised procedure, exact assertion, observed result and reference/variant identity. A rejection of a permitted variant can expose an extra constraint in the procedure; a rejection at an unrelated assertion does not demonstrate the intended fault sensitivity. Runtime errors and unavailable bindings remain distinct from those observations. An absence of execution is unobserved, not PASS; any correction changes the artifact revision and invalidates affected old receipts.

An independent reference or permitted variant has provenance separate from the procedure author and bounded source review for the scope being checked. An author's own unverified prototype is insufficient. Record the exact contrast and limitations; a fixture with a known defect cannot certify the affected scope. A narrow unaffected check does not clear that defect or qualify the whole fixture. Same-source or source/reference disagreements need attribution to the procedure, fixture or unresolved source; a green matrix cannot settle that meaning automatically. A reference or failed check supplies evidence, not a new requirement.

Execute only through an authorized suitable environment. API separation such as Node vm does not establish hostile-code confinement. A prior local check is not authorization to execute arbitrary generated code, start extra model sessions or install a runtime.

## Validate the whole requested result

Keep four conclusions distinct: source fidelity/coverage/authority/useful handoff; executable runtime correctness; bounded reference/fault sensitivity; and parity of an actual implementation. Passing a reference and detecting known faults supports only those observed contrasts. Counts, source-line citations and a complete manifest do not prove that every applicable clause or reachable history is covered.

Inspect the contract's requirements, gaps, freedoms and handoff against the original sources and actual procedures. Preserve concrete non-executable checks for obligations outside the binding. Classify the remaining work as an omitted procedure within current capabilities, an observation/API limitation, a reference limitation, an unobserved check or a genuine source/authority issue. These categories require different next actions; they are not interchangeable product gaps.

Apply the commissioned validation criteria to its full intended scope. Unobserved implementation evidence can remain a future evidence request; it cannot be reported as observed sensitivity or parity. An actual missing acceptance condition remains a completeness issue. The artifact creates no additional approval gate, contract effectivity or canon publication.

## Carry the exact artifact

The native acceptance index and requested views carry artifact ID/revision, accessible relative locator, tested code hash, controlling source revisions, API/runtime/environment, observed receipt locator and its precise coverage/limitations. Reuse actual applicable evidence under normal freshness rules. Materialize the code or exact locator without a second prose rendition of its setup/actions/assertions. Carry the other concrete checks and unobserved scope alongside it.

Consumer access to all current code and full controlling sources remains required. A local developer path is not proof of portable delivery. Fixture sensitivity is not real-product parity, review-ready is not effective, and publication of one record does not make another record effective.
