# Audit Design System

Reconstruct the observed system state. Assess maturity by scope and bring the owner an operating posture supported by evidence. Do not silently consume, invent, or replace rules.

## Packet mode

- **Carried:** use and update the supplied valid Design Work Packet. Do not reconstruct its intake or reread pinned authority merely to confirm it.
- **Direct single-skill:** when the System Assessment is the complete requested outcome, return it without creating a packet.
- **Direct expansion:** when direct system audit becomes a material or uncertain multi-skill chain, create exactly one [Design Work Packet](../references/packet-projections.md#design-work-packet) before the first downstream handoff.

Refresh a carried packet only when a required field is missing, a source is stale or conflicting, scope or authority changes, or genuinely new system evidence appears.

Without a valid packet, read [authority and status](../references/authority-and-status.md). Load the [Design-System Assessment template](../references/audit-exploration-templates.md) only when a durable assessment is required. Use [practical design checklists](../references/quality-checklists.md) only when the commissioned system lenses or impact need them.

Read [design-system craft](../references/design-system-craft.md) only when the task needs depth on token/theme relationships, component or pattern specifications, behavior/content/state contracts, documentation, adoption/drift, agent-ready context, or system evaluation.

## Assess observed state

Inspect the permitted combination of:

- documented canon;
- token/theme relationships;
- components and patterns;
- behavior/content/state contracts;
- accessibility and responsive behavior;
- documentation;
- agent-ready retrieval context;
- implemented surfaces;
- adoption receipts;
- exceptions, drift, and ownership;
- maintenance/evaluation signals.

Keep documented intent separate from observed implementation.

Classify maturity for the exact scope, with evidence:

- **healthy:** coherent, sufficiently complete, authoritative, and maintained for the scope;
- **partial:** useful authority exists but coverage or consistency has material gaps;
- **absent:** no adequate system authority exists for the scope;
- **harmful:** following the current system in the scope would preserve material user harm, contradiction, or inaccessible behavior.

Do not apply one label to an entire product when different scopes differ.

## Recommend an operating posture

- **consume:** use the current system unchanged for this scope.
- **extend:** add a missing approved pattern while preserving the healthy base.
- **repair:** correct deficient system rules or assets before relying on them.
- **constrain:** limit use to the safe subset and document prohibited or unreliable parts.
- **establish:** create the minimum new system authority needed where none exists.
- **replace-migrate:** approve a target and staged migration because repair cannot safely meet the need.

For the recommended posture, state scope, evidence, preserved strengths, debt, exceptions, permissions, alternatives, trade-offs, migration implications when relevant, and any owner decision required. Different scopes may use different postures.

When evidence supports **consume** and effective design-system canon already authorizes the exact scope, proceed under that canon. For this **consume** path, do not create a new owner decision or effectivity gate. For **extend**, **repair**, **constrain**, **establish**, or **replace-migrate**, use [evolve-design-system](evolve-design-system.md) once the posture is explicitly approved under the applicable authority policy.

## Continue useful work

Missing or harmful canon is not a generic refusal. Continue inventory, evidence collection, safe constraints, candidate comparison, bounded design exploration, and any scoped canon-change draft already authorized. Do not call improvised choices a system. If a material posture decision is unresolved, stop only the dependent effectivity or implementation handoff.

When a material posture is not already authorized, the assessment proposes it. The resulting canon change still requires human effectivity approval, even when its drafting is authorized. Do not stop after the audit when `consume` or an approved evolution path can safely continue.

In carried or direct-expansion mode, update the packet with:

- the current step;
- the System Assessment locator and revision;
- findings to preserve;
- maturity and posture;
- the approved or unresolved posture gate;
- the active sequence;
- the next step and stop.

Do not create a parallel context record. In direct single-skill mode, return the native assessment without a Design Work Packet.

Observing implementation, API, or data constraints does not activate operational workflows unless their trigger or stronger consumer policy applies.
